# 权限管理接口详细设计（设计稿）

本稿细化[接口全景](11-接口全景与实施批次.md)的 B 批次：用户、角色、部门、菜单、独立接口权限及授权。目标是可复用的单租户管理模板，逻辑路径不带浏览器代理前缀 `/api`。用户、角色、部门、菜单和接口权限管理接口均已实现。[唯一 OpenAPI 文件](openapi/核心接口.openapi.json)持续作为 Apifox 导入文件。

已实现的查询接口使用数据库实时校验权限。用户列表和详情分别按自身权限码计算有效角色的数据范围；`super_admin` 由服务端识别。分页结果按 ID 倒序，响应仅包含公开 DTO 字段。角色写入只允许有效超级管理员，角色授权在事务中锁定角色行并整体替换；角色写入的成功操作记录操作人、目标、权限码、请求 ID 与来源 IP。用户管理写入包含创建、资料修改、启停、角色替换、密码重置与本人资料修改；用户、角色、部门、菜单和接口权限管理页面均已接入。当前写操作已记录成功审计；失败审计和统一字段级校验错误响应仍待补全。

## 通用契约

- 认证：所有接口要求 Bearer Access Token。后台方法权限按表中的权限码校验；`super_admin` 由服务端特判全权，仍受保护规则约束。第一版用户角色替换、角色写入与授权、菜单与接口权限写入还要求当前用户拥有有效 `super_admin` 身份，不能只凭权限码执行。
- 包装：成功 `{"code":0,"data":...,"message":"ok"}`。列表的 `data` 为 `{"items":[],"total":0}`；创建和其他写操作返回 `data: true`。资源 ID 在查询接口中使用十进制字符串。
- 分页：`page` 从 1 开始，默认 1；`pageSize` 默认 20、最大 100。排序仅允许各端点定义的固定字段；不接受任意 SQL 字段名。树查询不分页。
- 状态：`ENABLED` 对应数据库 `1`，`DISABLED` 对应 `0`。状态接口使用 `PUT /{id}/status`，请求体只需 `{status}`。
- 并发：第一版不要求前端传乐观锁版本。单次更新在数据库事务中完成；授权集合替换时锁定所属用户或角色行，使同一目标的并发授权串行执行。普通资料编辑采用后提交覆盖先提交，管理员审计记录修改行为。若具体业务不能接受覆盖，再为该业务单独引入并发控制。
- 校验：非法枚举、缺失字段、越界长度返回 400 / `40000`；未认证 401 / `40100`；无权或超出可管理范围 403 / `40300`；对象不存在 404 / `40400`；唯一键冲突、树约束或被引用 409 / `40901`。字段错误通过 `data: {fieldErrors:[{field,message}]}` 表达；其他错误 `data: null`。
- 用户管理以 `sys_user.primary_dept_id` 和用户自身为数据范围边界，列表、详情和写入均做后端校验；角色、部门、菜单和接口权限是全局配置，不机械套用业务数据范围，但受功能权限及保护规则限制。仅隐藏前端按钮不构成授权。不得把数据库实体直接序列化给客户端。

## 用户

| 方法与路径 | 请求 | 响应 `data` | 权限码 |
|---|---|---|---|
| `GET /system/users` | `page,pageSize,username?,realName?,deptId?,status?` | `Page<UserSummary>` | `system:user:list` |
| `GET /system/users/{userId}` | 路径 ID | `UserDetail` | `system:user:view` |
| `POST /system/users` | `CreateUserRequest` | `{id}` | `system:user:create` |
| `PUT /system/users/{userId}` | `UpdateUserRequest` | `true` | `system:user:update` |
| `PUT /system/users/{userId}/status` | `{status}` | `true` | `system:user:status` |
| `PUT /system/users/{userId}/roles` | `{roleIds}` | `true` | `system:user:grant` |
| `POST /system/users/{userId}/reset-password` | `{temporaryPassword}` | `true` | `system:user:reset-password` |
| `PUT /user/profile` | `UpdateProfileRequest` | `true` | 已登录且仅本人 |
| `PUT /user/password` | `{oldPassword,newPassword}` | `true` | 已登录且仅本人 |

`UserSummary`：`id,username,realName,email,phone,primaryDeptId,primaryDeptName,status,createTime`。`UserDetail` 再包含 `avatarUrl,homePath,roleIds,updateTime`；从不包含 `passwordHash`。响应时间为数据库中的北京时间，输出 `yyyy-MM-dd HH:mm:ss` 字符串，不额外换算时区。

`CreateUserRequest`：`username`（3–64，字母/数字/下划线/点/连字符，建立后不可修改）、`realName`（1–128）、`email?`（有效邮箱，最长 255）、`phone?`（最长 32）、`primaryDeptId`（普通用户必填，须为启用中的部门）、`avatarUrl?`（最长 1024）、`homePath?`（须为已授权页面或留空）、`roleIds`（可为空且去重，不得包含 `super_admin`）、`status`。仅系统超级管理员可在创建时提交非空普通 `roleIds`；普通管理员必须提交空数组，不能绕过用户角色替换接口。创建时服务端固定使用初始密码 `12345678` 并仅存哈希，客户端不提交密码；新用户的 `must_change_password` 为 `1`，首次登录必须修改密码。`UpdateUserRequest` 为除 `username`、`roleIds`、`status` 外的资料字段，普通用户的 `primaryDeptId` 不可置空，系统超级管理员账号可保持空部门；其它可空字段可显式传 `null` 清空。状态只能通过专用接口修改。

`roleIds` 只接受启用的普通角色，空数组用于撤销全部普通角色。第一版整个用户角色替换接口仅系统超级管理员可调用；替换必须原子完成，不得包含 `super_admin`，也不得以系统初始化账号为目标。`super_admin` 只能由首次初始化流程绑定。普通管理员不得修改、停用或重置拥有 `super_admin` 角色的用户。账号启停仅允许拥有 `system:user:status` 的管理员在其数据范围内操作；没有该权限的普通用户不能启停其他账号。任何用户都不能停用自己的账号；前端将该行的“禁用”操作置灰，后端按当前登录用户 ID 校验。停用其他用户或重置密码后撤销目标用户的全部会话。重置密码请求体为 `{temporaryPassword}`（8–128 位，由管理员设置），服务端只存自适应哈希并设置 `must_change_password=1`；密码由管理员通过线下受控渠道交付，不在响应或日志中回显。普通管理员重置密码时仍需满足当前目标用户的数据范围与目标保护规则。

个人资料只允许修改 `realName,email,phone,avatarUrl`；修改密码必须校验旧密码，新密码至少 8 位，成功后撤销全部会话（包括当前会话）并要求重新登录，确保首次改密和正常改密都由服务端强制生效。两个接口都不能指定目标用户 ID。

## 角色与授权

| 方法与路径 | 请求 | 响应 `data` | 权限码 |
|---|---|---|---|
| `GET /system/roles` | `page,pageSize,roleCode?,roleName?,status?` | `Page<RoleSummary>` | `system:role:list` |
| `GET /system/roles/{roleId}` | 路径 ID | `RoleDetail` | `system:role:view` |
| `POST /system/roles` | `CreateRoleRequest` | `{id}` | `system:role:create` |
| `PUT /system/roles/{roleId}` | `UpdateRoleRequest` | `true` | `system:role:update` |
| `DELETE /system/roles/{roleId}` | 路径 ID | `true` | `system:role:delete` |
| `GET /system/roles/{roleId}/menus` | 路径 ID | `{menuIds}` | `system:role:grant` |
| `PUT /system/roles/{roleId}/menus` | `{menuIds}` | `true` | `system:role:grant` |
| `GET /system/roles/{roleId}/permissions` | 路径 ID | `{permissionIds}` | `system:role:grant` |
| `PUT /system/roles/{roleId}/permissions` | `{permissionIds}` | `true` | `system:role:grant` |
| `GET /system/roles/{roleId}/data-scope` | 路径 ID | `{type,deptIds}` | `system:role:data-scope` |
| `PUT /system/roles/{roleId}/data-scope` | `{type,deptIds}` | `true` | `system:role:data-scope` |

`RoleSummary`：`id,roleCode,roleName,status,dataScopeType,createTime`；详情增加 `description,updateTime`。界面将 `description` 显示为“备注”。创建必须给 `roleCode`（3–64，创建后不可改）、`roleName`（1–128）、`description?`、`status`；默认数据范围为 `SELF`。创建和更新可选传 `menuIds`（完整的菜单与按钮 ID 集合），与角色资料在同一事务保存；空数组表示清空授权，更新时省略则保持现有授权。数据范围仍走专用接口。

第一版角色写入、两类授权和数据范围设置仅 `super_admin` 可执行。两类授权分别提交完整 ID 集合，在事务中原子替换；目标须存在且启用。页面授权为显示路由补齐父目录，但不自动授予按钮。按钮 `authCode` 与对应接口使用同一码；无按钮的接口码登记在 `sys_permission`。接口与码的映射写在后端代码中，数据库不能配置任意 URL 绕过鉴权。

数据范围 `type` 仅允许 `ALL`、`DEPT_AND_CHILDREN`、`DEPT`、`SELF`、`CUSTOM`。仅 `CUSTOM` 允许非空 `deptIds`；其他类型必须传空数组。执行某个权限码对应的操作时，只合并授予该码的有效角色的数据范围。`super_admin` 的资源和范围由应用层内置，不允许删除、停用或编辑其关键属性；普通角色若仍被用户引用，不允许删除。

## 部门

| 方法与路径 | 请求 | 响应 `data` | 权限码 |
|---|---|---|---|
| `GET /system/depts/tree` | `status?` | `DeptNode[]` | `system:dept:list` |
| `GET /system/depts/{deptId}` | 路径 ID | `DeptDetail` | `system:dept:view` |
| `POST /system/depts` | `CreateDeptRequest` | `{id}` | `system:dept:create` |
| `PUT /system/depts/{deptId}` | `UpdateDeptRequest` | `true` | `system:dept:update` |
| `DELETE /system/depts/{deptId}` | 路径 ID | `true` | `system:dept:delete` |

部门树的 `status` 筛选保留命中部门的祖先节点；兄弟节点按 `sortOrder,id` 排序。详情包含该部门子树。

`DeptNode`：`id,parentId,deptCode,deptName,sortOrder,status,remark,createTime,children`；详情再含 `updateTime`。创建/更新字段为 `parentId?`、`deptName`（1–128）、`sortOrder`（整数）、`status`、`remark?`（最多 500 字符）。`deptCode` 不由客户端传入；创建事务中获得部门 ID 后按 `app.dept.code-prefix`（默认 `DEPT_`）加至少四位数字生成，例如 `DEPT_0001`，超过四位自然扩展。编码不回收，删除或失败操作可能造成空号；历史编码保持不变。根部门 `parentId=null`。部门状态只作用于该节点，不向下级继承；禁用部门可以新增下级或接收移动的部门，移动时仍校验父节点存在且不在自身子树中。删除仅允许已禁用、无子部门、无用户归属、无角色自定义范围引用的部门；直接归属该部门的启用用户存在时，禁止停用该部门。

## 菜单与独立接口权限

| 方法与路径 | 请求 | 响应 `data` | 权限码 |
|---|---|---|---|
| `GET /system/menus/tree` | 无 | `MenuNode[]` | `system:menu:list` |
| `GET /system/menus/{menuId}` | 路径 ID | `MenuDetail` | `system:menu:view` |
| `POST /system/menus` | `CreateMenuRequest` | `{id}` | `system:menu:create` |
| `PUT /system/menus/{menuId}` | `UpdateMenuRequest` | `true` | `system:menu:update` |
| `DELETE /system/menus/{menuId}` | 路径 ID | `true` | `system:menu:delete` |
| `GET /system/permissions` | `page,pageSize,permissionCode?` | `Page<PermissionView>` | `system:permission:list` |
| `GET /system/permissions/{permissionId}` | 路径 ID | `PermissionView` | `system:permission:view` |
| `POST /system/permissions` | `CreatePermissionRequest` | `{id}` | `system:permission:create` |
| `PUT /system/permissions/{permissionId}` | `UpdatePermissionRequest` | `true` | `system:permission:update` |
| `DELETE /system/permissions/{permissionId}` | 路径 ID | `true` | `system:permission:delete` |

`MenuNode` 包含 `id,parentId,type,menuKey,routeName,routePath,component,redirectPath,authCode,titleKey,icon,sortOrder,routeMeta,status,children`。类型为 `CATALOG/MENU/BUTTON/EMBEDDED/LINK`；按钮必须有 `authCode` 且不设置路由。目录、页面、内嵌和外链须有合法路由；普通页面组件须在已打包清单，内嵌和外链的 HTTP/HTTPS 地址分别使用 `routeMeta.iframeSrc` 和 `routeMeta.link`。详情增加时间字段。菜单停用使后代路由和按钮码失效；删除要求无子节点、无角色授权、无关联接口权限。

`PermissionView` 包含 `id,menuId,permissionKey,permissionCode,titleKey,sortOrder,status,createTime,updateTime`。`menuId` 仅用于归类，不进入菜单树。更新不能修改 `permissionKey` 和 `permissionCode`。权限码不得与按钮 `authCode` 重复；删除要求无角色授权。

## 校验与事务边界

1. 用户角色、角色菜单与接口权限、角色自定义部门范围均在**单个数据库事务**中原子替换；修改前锁定所属用户或角色行，并在同一事务中校验目标状态与保护规则。
2. 第一版不缓存授权决策；下一次受保护请求直接读取 MySQL 已提交状态。Redis 故障时验证码与登录限流不可绕过，登录失败关闭。
3. 用户状态、角色状态、菜单与接口权限状态都影响有效权限；直接请求 API 必须在服务端重新校验。审计记录操作人、目标、权限码、结果与请求 ID，不保存密码或令牌。
4. `super_admin` 角色本身不可变，只能绑定首次初始化账号；用户管理接口不得再授予或撤销它。禁止停用最后一个可登录的系统超级管理员。
5. 删除采用受限物理删除：角色、部门、菜单与接口权限只有未被引用时才允许。用户第一版不提供删除接口，以保留审计关联。

## 数据库核对

V4 新增 `sys_menu`、`sys_permission`、`sys_role_menu`、`sys_role_permission`，从 V1–V3 的资源表迁移并保留旧 ID 与授权。历史迁移不回改。跨表权限码唯一性、树无环、管理员保护和数据范围由服务层校验。

## 与 Apifox 的交付

只维护最初的[OpenAPI 3.0 文件](openapi/核心接口.openapi.json)，现包含 46 个操作。业务接口实现后以 springdoc 生成的 OpenAPI 为代码事实源，核对并覆盖这一份文件；Apifox 按稳定 `operationId` 更新已有接口。已实现接口仍与同一份 Apifox JSON 契约对照；未另建导入文件。
